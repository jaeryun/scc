# common/ — 모든 뷰의 공통 기반

이 디렉토리는 특정 뷰에 귀속되지 않고 프로젝트 전체가 공유하는 문서를 담습니다.

## 디렉토리 구조

| 디렉토리 | 목적 | 파일 배치 |
|----------|------|-----------|
| `foundation/` | 프로젝트 헌장 — 정체성, 제약, 핵심 결정사항 | 플랫 (주제당 1파일) |
| `development/` | 코딩 규칙 + 구현 패턴 — 모든 코드 작성 가이드 | 플랫 (하위 디렉토리 금지) |
| `operations/` | 빌드, 배포, 장애 대응, 모니터링 | 플랫 |
| `reference/` | 참조 자료 — API, 데이터 모델, 환경변수 | 하위 디렉터리 허용 (유일) |
| `decisions/` | 아키텍처 결정 기록 (ADR) | 플랫, 시간 순 |

> 파일 유형별 상세 규칙은 [docs.md](development/docs.md) 참조.

## AI 탐색: 결정 트리

새 문서를 어디에 넣을지 판단이 안 되면 아래 트리를 따른다.

```
문서의 주제가...
├── "이 프로젝트는 무엇인가?" (정체성, 철학, 제약)
│   → foundation/
│
├── "코드를 어떻게 작성하는가?" (규칙, 패턴, 컨벤션)
│   → development/
│
├── "어떻게 배포/운영하는가?" (빌드, 배포, 장애 대응, 모니터링, 런북)
│   → operations/
│
├── "무엇이 존재하는가?" (API 명세, DB 스키마, env 목록, 데이터 계약)
│   → reference/
│
├── "왜 이렇게 결정했는가?" (ADR, 기술적 트레이드오프)
│   → decisions/
│
├── "어떻게 테스트하는가?" (테스트 전략, 픽스처, 모킹 가이드)
│   → development/ (코드 관련) 또는 operations/ (E2E/통합 테스트)
│
├── "보안/컴플라이언스 관련" (취약점 대응, 인증 정책)
│   → foundation/ (정책) 또는 operations/ (대응 절차)
│
└── 특정 뷰(dcim, demo, settings, home)의 사용자 워크플로우인가?
    → views/<view>/
```

## views/ vs common/ 경계

**핵심 질문: "이 문서가 기술하는 것은 계약(contract)인가, 사용법(usage)인가?"**

| 문서 성격 | 위치 | 예시 |
|-----------|------|------|
| **계약/스펙** (데이터의 구조, API의 입출력) | `common/reference/` | IPAM API 명세, Subnet 타입 정의, env 변수 목록 |
| **규칙/패턴** (코드 작성 방법) | `common/development/` | "TanStack Form으로 폼 작성하는 법", "네이밍 컨벤션" |
| **워크플로우/사용법** (특정 뷰에서의 작업 절차) | `views/<view>/` | "DCIM에서 서브넷 추가하는 법", "설정 화면에서 테마 변경하기" |

**헷갈리면:** "이 문서를 다른 뷰의 개발자가 봐야 하는가?" → 예면 `common/`, 아니오면 `views/<view>/`.

**API는 처음에 한 뷰에서만 사용되어도 `common/reference/api/`에 둔다.** API는 본질적으로 계약이며, 소비자가 늘어나는 건 시간 문제다.

**정말 애매하면:** 좁은 범위(`views/`)에 먼저 두고, 실제로 공유 필요성이 생기면 `common/`으로 승격한다.
